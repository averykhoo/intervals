# the IEEE 1788 layer: open questions for the owner (2026-10-03)

advice for Q13 (a)-(e) with Q9/Q10 folded into (c)/(d), open item 6 `layer-numpy`, and the
departures census bullet. read-only session; probes under `.scratch/owner-questions/probes-1788/`.
"verified" = run by probe today; "inferred" = read from source/plan.

sections are appended as written; a missing section below is not yet written.

## 0. who uses a 1788 layer, and what they need

three audiences, in the order of how much they would use `intervals.ieee1788` (inferred; the
library has no users yet, so this is the set of people a 1788 layer exists for at all):

1. **porters**: someone moving code from libieeep1788 (C++), GNU Octave's `interval` package, Julia's
   IntervalArithmetic.jl or MPFI, who expects 1788's *names* (`mulRevToPair`, `cancelMinus`,
   `overlap` with sixteen states), 1788's *answers* (closed binary64 ends, infinity never attained,
   `cancelMinus` entire as "no answer", `mid(∅)` NaN) and 1788's *errors* (a bare and a decorated
   interval never meet). what they need is that one 1788 statement has one answer in the layer and
   that the answer is 1788's, so a port is mechanical. libieeep1788's own C++ spelling is
   snake_case free functions (`mul_rev_to_pair`, `cancel_minus`, `is_common_interval`; background
   knowledge, not verified in this tree), so the layer's spelling is theirs already.
2. **people who want a conformance claim**: the layer is the only place the package can say "this
   is 1788-2015, set-based flavour, inf-sup binary64, bare and decorated". what they need is the
   exact third pass (`tests/itf1788/test_ieee1788.py`, 9542 vectors compared exactly, 104 vectors
   under 94 rows of three owner-approved categories, 2026-09-28) and a written list of what is
   missing (NaI, the recommended ops, the exact/interchange text conversions, other formats), which
   `intervals/ieee1788.py`'s docstring already has. a conformance statement is mostly documentation.
3. **the library's own solver users, indirectly**: `mulRevToPair`'s split is what an interval
   newton wants; here that is served by the library's `mul_rev` (pieces, exact), not the layer, so
   this audience touches the layer only to compare against a 1788 reference.

what none of them needs: 1788 answers *inside* the library's classes. the 2026-08-16 principle
("a wrapper, never a mode", `v2-plan.md` "the 1788 layer") is right for all three; every
recommendation below keeps it.

## 1. Q13 (a) shape and export

**built today** (verified 2026-10-03): `intervals/ieee1788.py`, one class `Interval(lo, hi,
decoration)` for bare (`decoration=None`) and decorated; 104 snake_case functions, builtins with a
trailing underscore (`abs_`, `min_`, `max_`, `pow_`, `sum_`); `ieee1788.NAMES` maps 1788's camelCase
to each (`ieee1788.py::NAMES`, 104 keys). not in `intervals.__all__` and not imported by
`intervals/__init__.py` (pinned by `tests/test_ieee1788_layer.py::test_not_exported`); `from
intervals import ieee1788` works because python imports a submodule on request. the module imports
only modules `intervals/__init__.py` already loads (`decorated`, `literals`, `reverse`,
`reductions`, `kernel`, `rounding`), so exporting it would cost one small module's load, no new
dependency.

three independent sub-choices: the class shape, the names, the export.

### (a1) one class or two

* **one class, flavour by `decoration is None`** (built). meaning: `Interval(1, 2)` bare,
  `Interval(1, 2, 'com')` decorated, `_flavour()` raises `TypeError` on a mixed call. pros: half the
  surface, one `NAMES`, one `from_set`; a number beside a decorated operand becomes newDec's point
  automatically (`ieee1788.py::_interval_of`). cons: `isinstance` cannot tell the flavours apart and
  a type annotation cannot either; `Interval(1, 2) != Interval(1, 2, 'com')` is correct (1788's types
  differ) but surprises; porters from libieeep1788 / Octave (`infsup` vs `infsupdec`) / Julia
  (`Interval` vs `DecoratedInterval`) expect two types. better when: the layer is a reference and a
  test rig first, a port target second (today).
* **two classes** (`BareInterval`, `DecoratedInterval`, or a subclass pair). pros: mirrors 1788's
  two types and every other implementation; static typing. cons: every function dispatches on the
  class anyway (the library computes the same way), so it is surface without behaviour; the
  library already has a `DecoratedInterval` and a second class of that name in the package would be
  a trap. better when: a typed port from libieeep1788 is the main use.

recommendation: **keep one class** (confidence ~75%). what would change my mind: a user porting
typed code. cost later: splitting the class after 2.0 breaks every `Interval(...)` call that passes a
decoration; it is the one part of (a) that has to be decided before release.

### (a2) names

* **snake_case + `NAMES`** (built). a trailing underscore on the five builtins is python's
  convention; `NAMES['mulRevToPair']` serves anyone generating calls from 1788 text (the third pass
  does exactly that). the camelCase aliases as module attributes would double the namespace for no
  behaviour. recommendation: **keep** (confidence ~90%). cost later: additive aliases are free at
  any time; renames are not.

### (a3) export

* **not exported, not imported by `intervals`** (built). meaning: `import intervals;
  intervals.ieee1788` is an `AttributeError` until `from intervals import ieee1788` runs. pros: the
  package's namespace states the library's semantics only; the layer is visibly a separate thing;
  nothing above the library is loaded by people who never use it. cons: discoverability (a reader
  of `dir(intervals)` does not see it); the README already names the import line (README line 83).
* **import the submodule in `__init__`** (one line, `from intervals import ieee1788 as ieee1788`,
  not in `__all__`). pros: `intervals.ieee1788.sqrt(...)` works after `import intervals`; no name of
  the layer enters the top namespace (not `Interval`). cons: a layering inversion in letter (the
  library imports what sits above it; harmless since the module is a leaf); `test_not_exported`
  is rewritten; roughly one more module at import.
* **export the class** (`from intervals import Interval`): rejected: a plain `Interval` beside
  `MultiInterval` reads as the library's own type and it is not.

recommendation: **keep not exported for 2.0** (confidence ~65%); it is additive to export later,
destructive to un-export. what would change my mind: the owner wanting the conformance story front
and centre in the package (then the one-line submodule import, never the class).

## 2. Q13 (b) numbers of the empty set

**built today** (verified 2026-10-03, `probes-1788/probe1.py`): `ieee1788.mid/rad/wid/mag/mig/
mid_rad(Interval())` each raise `ValueError` ("the empty set has no midpoint" ...); `inf(∅)` is
`+inf`, `sup(∅)` `-inf` (1788's). the vendored vectors expect `NaN` for the numbers of `[empty]`
(`libieeep1788_num.itl`, 20 `NaN` statements; `libieeep1788_reduction.itl`, 8). the third pass reads
"a `ValueError` from a number or a reduction" as `NaN`, and only where the vector expects `NaN`
(`tests/itf1788/test_ieee1788.py::NAN_READ`, `::test_the_nan_reading_is_narrow`): a translation
rule in the test, i.e. the pass is matching 1788 through an adapter clause the layer itself does
not implement. the layer also already answers 1788's way where the library would not for other
numbers: `inf([0, 1])` is `-0.0` (`ieee1788.py::inf`, "1788's rule", pinned by
`tests/test_ieee1788_layer.py::test_the_sign_of_zero_is_1788s`) while the package has one zero.

* **raise `ValueError`** (built). meaning: the layer's numbers are the library's (D9) through
  `float()`. pros: one rule for every number in the package; a python caller never gets a silent
  nan; D9 and Q2 were owner decisions and the layer inherits them. cons: contradicts the layer's own
  principle (e) ("where 1788 defines another answer, the layer gives 1788's"), which the layer
  applied to the sign of zero, a far smaller thing; a porter's `if isnan(mid(x))` becomes an
  exception; the conformance story needs the footnote "numbers of the empty set raise instead of
  NaN"; the pass needs its `NAN_READ` clause for the layer forever.
* **return `nan` in the layer only** (1788's answer). meaning: `_number` and `mid_rad` catch the
  library's `ValueError` on the empty set and return `math.nan` (`(nan, nan)` for `mid_rad`); the
  library is untouched (D9 stands). pros: the layer answers 1788's way everywhere, so its contract
  is one sentence; the third pass's `NAN_READ` becomes unnecessary for the numbers (keep it for the
  library's adapter, `tests/itf1788/test_itf1788.py`), so the pass compares the layer with no
  translation at all; porters get what they test for. cons: a nan is quiet in python; a second
  answer in the package for `mid(∅)` (but that is exactly what (e) already does for `cancel_minus`
  and `overlap`). better when: the layer is a port target or a conformance claim (audiences 1 and
  2), which is what it is for.
* **return `nan` in the library too**: rejected, D9 was decided by the owner on the library's own
  grounds (`mid` as a bisection point must never be a nan).
* a sub-choice if `nan` is taken: **the reductions**. `ieee1788.sum_ is intervals.sum_`
  (`ieee1788.py` "REDUCTIONS"), which raises where 1788 says `NaN` (a nan operand, `inf + -inf`,
  `0 * inf`; 8 vectors). for the same consistency the layer would wrap the four reductions
  (catch `ValueError`, return `nan`, ~6 lines) rather than re-export the objects. pros: the layer's
  rule is then total. cons: the raise there is about invalid *input* (nan operands), where a loud
  failure is more defensible than for the empty set. I would do it with the numbers so the pass
  needs no `NAN_READ` for the layer at all, but it is the weaker half (confidence ~55%).

recommendation: **return `nan` in the layer** for the six numbers (confidence ~70%); the
reductions with them, lower confidence. what would change my mind: the owner reading the layer as a
test rig first (then raising is fine and the pass's clause is the right place for the translation).
cost later: either direction is a semantic change after 2.0 (`raise` to `nan` breaks a
`try/except ValueError`, `nan` to `raise` breaks `isnan` checks); decide before release. cost now:
~10 lines in `ieee1788.py`, the `NAN_READ` clause narrowed or removed in
`tests/itf1788/test_ieee1788.py`, `::test_numbers`/`::test_numbers_examples` and the module docstring
updated; the gate's `gate:itf` and `gate:rest` both stale.

## 3. Q13 (c) = Q9: mulRevToPair's decoration

**built today** (verified 2026-10-03, `probe1.py`, `probe2.py`): `ieee1788.mul_rev_to_pair(b, c)`
is 1788's pair: where `0 ∉ b`, `(div(c, b), [empty]_trv)` with the first decorated as the division
(`([0.2, 21.0]_dac, [empty]_trv)` for `[-2, -0.1]_dac`, `[-2.1, -0.4]_dac`; `com` for `[1, 2]_com`,
`[1, 2]_com`); where `0 ∈ b`, the real pieces of the library's `mul_rev`, each trv
(`([-inf, -1.0]_trv, [1.0, inf]_trv)` for `[-1, 1]_dac`, `[1, 2]_dac`). the library's `mul_rev` is one
op, trv on decorated operands (`[0.2, 21.0)_trv`; the open end is the rounded one, see §7).
`ieee1788.mul_rev` (1788's `mulRev`) is trv too, as 1788 has it (`libieeep1788_rev.itl:988`).
census of the vendored pair vectors (`libieeep1788_mul_rev.itl`): 347 statements, 174 decorated;
of the decorated non-NaI ones the first interval is `trv` in 120, `dac` 41, `com` 6, `def` 5
(the 52 `DECORATION_ONLY` rows, `tests/itf1788/test_itf1788.py::DECORATION_ONLY`, asserted 52 at
`:898`); every two-piece decorated result (16) is `trv trv`. the third pass matches all 347 through
the layer with no row.

* **as built: the pair with 1788's decoration lives in the layer; the library's `mul_rev` stays one
  trv op; the adapter's 52 rows stay** (`_PAIR_DECORATED_AS_DIVISION`). pros: sound on both sides
  (trv claims nothing of the library's set; the layer's `div` decoration is computed by the decorated
  division itself, not copied); the rows are true statements about the library and each has the
  second reading "1788's own answer is `ieee1788.mul_rev_to_pair`, which matches" (`v2-plan.md`
  "the 1788 layer", last bullet); nothing new on the core. cons: a reader of the adapter sees 52
  rows for something the package does answer; the row's reason does not yet say where (HANDOFF
  "still owed", M16b: one clause each in the adapter's docstring and in
  `_PAIR_DECORATED_AS_DIVISION`).
* **a pair op on the library** (`mul_rev_to_pair` on `MultiInterval`/`DecoratedInterval`, decorated
  as the division where `0 ∉ b`). cons, each measured: (1) in the library ±inf are points, so the
  set is not the division's where `0 ∉ b` (`mul_rev([1, inf], [inf])` is `(0, inf]`, `[inf] / [1,
  inf]` is `[inf]`, verified today); a decoration copied from the division would claim `dac`/`com`
  for a set that is not the division's: unsound; (2) a multi-piece `b` gives more than two pieces, so
  "pair" has no meaning on the core (the layer raises `AssertionError` past two pieces for 1788-form
  operands, `ieee1788.py::mul_rev_to_pair`); (3) a port that wants the pair wants 1788's ends and
  closedness too, which only the layer gives. no audience is served that the layer does not serve
  better.
* **decorate the library's `mul_rev` as the division where `0 ∉ b`**: the same unsoundness as above,
  and 1788 itself decorates `mulRev` trv, so the library would then disagree with 1788 where today it
  agrees.
* **drop the 52 rows by routing the adapter's decorated pair vectors through the layer**: changes
  what the adapter tests (the library) to make a count smaller; the third pass already runs them.

recommendation: **close Q9 as built** (confidence ~90%), and pay the two owed clauses (the adapter
docstring naming the third pass; `_PAIR_DECORATED_AS_DIVISION` naming `ieee1788.mul_rev_to_pair`)
plus the README row "mulRevToPair's decoration ... Q9 open (pending Q13(c))" (README line 272) and
D21(c) marked decided. what would change my mind: nothing I can see; the two alternatives are
unsound on the library's own semantics. cost later: none, the layer's pair is already 1788's;
the clauses are markdown and a string constant (a string edit in `test_itf1788.py` stales
`gate:itf`, ~1 min).

## 4. Q13 (d) = Q10: the constructors' outward pass

**built today** (verified 2026-10-03): the library's `text_to_interval('[0.1, infinity]')` is the
exact set `[1/10, inf)` as a `MultiInterval`, `nums_to_interval(Fraction(1, 10), 1)` is `[1/10, 1]`;
the layer's `ieee1788.text_to_interval` is `[0.09999999999999999, inf]` and `Interval(Fraction(1,
10), 1)` is `[0.09999999999999999, 1.0]`, 1788's binary64 hull. in the adapter the four constructors
(`tests/itf1788/test_itf1788.py::CONSTRUCTORS`, 201 interval-valued vectors) run in the plain pass
only; in the layer's pass they run exactly through the layer, with 9 rows (7 "exact parsing decides
validity", 2 "no NaI"), both owner-approved categories (D16, D18(b)). the M13g review's wording was
"a class argument (an `OutwardMultiInterval` result, 1788's binary64 hull)" (plan §2 M13g "owner
questions", item 2).

* **as built: the binary64 run is the layer's; the library's constructors return the exact set, no
  class argument.** pros: the library's rule "an exact operand never loses its true value"
  (`v2-plan.md` "arithmetic") holds for literals too; the hull is one call away
  (`ieee1788.text_to_interval(t).to_set()` is an `OutwardMultiInterval` in 1788's form); every
  constructor vector is checked in binary64 somewhere (the layer's pass), which is what Q10 asked
  for. cons: a library user wanting the double hull of a literal must go through the layer or
  `ieee1788.from_set`; the README row "constructors ... Q10 open" (README line 269) is stale once
  closed.
* **a class argument on the library's constructors** (`text_to_interval(text,
  cls=OutwardMultiInterval)`). the name is a misnomer: `OutwardMultiInterval` with exact ends keeps
  them exact (the class rounds computed float results, not exact operands), so `cls=` would give the
  exact set in the other class, not the binary64 hull. to give the hull the argument would have to be
  a rounding flag (`round_to_doubles=True`) or a method (`A.hull64()`), i.e. the layer's `_hull`
  moved into the library as a second output rule. pros: an outward item for 201 vectors in the
  adapter. cons: new API whose only consumer is a test; two places that round to binary64; "the
  exact set" stops being the one answer of the library's constructors. better when: a library user
  (not a porter) repeatedly wants 1788-form sets without importing the layer; nobody has asked.
* **a `MultiInterval` method `to_1788_hull()`** (a general outward-to-doubles hull, the layer's
  `_hull` as public API). the same as above with a better name; worth it only if something in the
  library besides the layer needs it. not today.

recommendation: **close Q10 as built** (confidence ~85%). what would change my mind: a second
consumer of the binary64 hull inside the library (a solver output step, say); then expose `_hull`
as a method and point the layer at it, still with no class argument on the constructors. cost
later: additive at any time (a flag or a method), so nothing is lost by waiting. owed when closed:
README line 269, D21(d), the HANDOFF Q10 entry.

## 5. Q13 (e) two answers to one 1788 name

**built today** (verified 2026-10-03): `ieee1788.cancel_minus([0, 1], [0, 2])` is `[entire]` where
`MultiInterval(0, 1).cancel_minus(MultiInterval(0, 2))` is `{}`; `ieee1788.overlap([1, 2], [2, 3])`
is `Overlap.MEETS` where `.allen()` is `Allen.OVERLAPS`; `ieee1788.log([-inf, 0])` is `[empty]`
where the library's is `[-inf]`; `ieee1788.inf([0, 1])` is `-0.0` where the package has one zero.
each module's docstring says which answer it gives (`ieee1788.py` "where 1788 defines another
answer"; README "departures from ieee 1788" lists the rows). the third pass matches every
cancellation (94 vectors), overlap (7) and infinity (63) vector through the layer with no row (plan
§2 M16b record: each rule off alone brought its rows back).

* **as built: the layer answers 1788's way, the library its own.** pros: this *is* the layer; the
  alternative is not a 1788 layer. the library's answers are owner decisions on the library's own
  grounds (D13 the Minkowski difference, D1/D6 infinities as points, the cut-based relations). a
  porter gets 1788, a library user gets sets, and the conversion between them is one function
  (`from_set`, `to_set`). cons: the same identifier (`cancel_minus`) means two things in one package,
  which a reader can trip on; the fix is the docstrings, already written.
* **the library adopts 1788's answers**: reverses D13 and the infinity model for the sake of a name;
  the library would lose real answers (`cancelMinus([-inf, -1], [-1, 5])` is `(-inf, -6]` here,
  "no answer" in 1788). rejected.
* **the layer answers the library's way where they differ**: the third pass would gain the 94 + 7 +
  63 rows the adapter has, the layer would stop being a conformance claim. rejected.
* **rename the library's divergent functions so no name has two answers** (e.g. the library's
  `cancel_minus` as `minkowski_difference`, keeping `cancel_minus` as an alias or dropping it).
  pros: removes the one real confusion. cons: D13 chose the 1788 name on purpose ("for connected A
  and B it is exactly 1788's answer whenever 1788 has one"); a rename churns the README, the plan
  and the adapter; `overlap`/`allen` and `log` are already different names. a marginal gain; I
  would not.

recommendation: **keep as built** (confidence ~90%). what would change my mind: nothing short of
redefining what the layer is for. cost later: none (the layer's answers are 1788's and 1788-2015 is
not changing); the library's side is covered by its own decision rows.

## 6. open item 6 layer-numpy

**built today** (verified 2026-10-03, numpy 2.5.2, `probes-1788/probe_numpy.py`):
`ieee1788.Interval.__array_ufunc__ = None` (`ieee1788.py:143`, pinned by
`tests/test_ieee1788_layer.py::test_the_class`). what works: `np.float64(2) + x`, `x +
np.float64(2)`, `np.int64(2) * x` (numpy defers to the reflected dunders, the numpy scalar is a
`numbers.Real` and the input rule takes it: `Interval(3.0, 4.0)`); an object array of `Interval`s
with `+ 1`, `* np.float64(2)`, `.sum()` (python's operators element by element). what refuses:
`np.add(x, x)` and `np.sqrt(x)` (`TypeError: operand 'Interval' does not support ufuncs`), and
`np.sqrt(np.array([x, x]))` (`loop of ufunc does not support ... no callable sqrt method`: numpy's
object loop looks for a *method*, and the layer has functions only). mixing with the library is a
`TypeError` by design (`x + MultiInterval(1, 2)`). the three core classes have
`numpy_compat.array_ufunc` (M16d, D23), whose "ours" test is `type(x).__array_ufunc__ is
array_ufunc` and whose non-operator table maps a ufunc to a **method name** on the operand
(`numpy_compat.py::_METHODS`, `::_SYMMETRIC`, `::_method`), so the shared hook cannot simply be
assigned to the layer's class: `np.sin(x)` would reach `getattr(x, 'sin')` and find nothing.

* **keep refusing** (built). meaning: 1788 intervals are scalars that do not speak ufunc; numpy
  scalars still work as numbers through the reflected dunders. pros: zero code; `__array_ufunc__ =
  None` is numpy's documented way to say exactly this; the layer's own form (one piece, closed
  doubles) is served by its functions, and a 1788 porter calls `ieee1788.sqrt`, not `np.sqrt`;
  additive to change later. cons: a porter from Octave/Julia who keeps *arrays* of intervals and
  writes `np.sqrt(arr)` gets a `TypeError` where `arr * 2` worked, an inconsistency inside numpy's
  own idioms; the core classes and the layer now differ on a visible rule, and the comment at
  `ieee1788.py:143` is the only place that says so.
* **give the layer its own hook** (not `numpy_compat.array_ufunc` as is). meaning: a small
  `__array_ufunc__` in `ieee1788.py` that reuses the operator protocol (`numpy_compat._operator`
  needs `_ours` generalised from an identity check to "has a hook of ours", a ~3-line change there)
  and maps the method ufuncs to the module's functions (`np.sqrt` -> `ieee1788.sqrt`, `arcsin` ->
  `asin`, `rint` -> `round_ties_to_even`, `minimum/maximum` -> `min_/max_`, `hypot`, `arctan2` ->
  `atan2`, `square` -> `sqr`, `reciprocal` -> `recip`), plus the elementwise object-array path
  (`np.frompyfunc`, already written in `numpy_compat.array_ufunc`). roughly 40-60 lines and a
  parametrised test in the shape of `tests/test_numpy_compat.py::test_unary_ufunc_is_the_method`.
  pros: one numpy rule for every type in the package; array-of-intervals ports work. cons: a second
  ufunc table to keep in step with the first; the layer stops being "the library through two rules
  and nothing else"; D23's choices (a foreign real is exact, `==` never broadcasts, `invert` the
  complement: the layer has no complement, so `np.invert` must refuse) have to be re-decided for the
  layer one by one. better when: a user with object arrays of `ieee1788.Interval` shows up; or the
  owner wants "numpy works the same on every type here" as a 2.0 statement.
* **give the layer methods too, then share the hook as is** (an `Interval.sqrt()` beside
  `ieee1788.sqrt`): doubles the layer's surface for numpy's sake; libieeep1788's API is functions.
  rejected.
* **operators only** (a hook that answers the operator ufuncs and declines the rest): buys
  `np.add(x, y)`, which nobody writes, and leaves `np.sqrt(arr)` red. not worth its own rule.

recommendation: **keep refusing for 2.0** (confidence ~65%) and say so in one line of the README's
numpy section ("the 1788 layer's `Interval` is a scalar to numpy: operators with numpy scalars work,
ufuncs do not"), so the rule is documented rather than a code comment. what would change my mind:
one porter with arrays of intervals, or the owner wanting the uniform statement; then the second
option as a small M16d follow-up. cost later: additive, low; the one behaviour that moves is
`np.float64(2) + x`, which goes from python's reflected path to the hook, and `numpy_compat`'s
hook reproduces python's protocol so the answer is the same (pinned for the core by
`tests/test_numpy_compat.py::test_numpy_scalar_operators_are_python_numbers`).

### 7.1 step functions as point sets

**verified 2026-10-03**: `MultiInterval.parse('[-1.5, 1.5]').floor()` is `{[-2], [-1], [0], [1]}`;
1788's answer is `[-2, 1]`; `ieee1788.floor(Interval(-1.5, 1.5))` is `[-2.0, 1.0]` (the output
rule hulls it, no warning). `floor([0, 999.5])` is 1000 points; `floor([0, 1000.5])` is the hull
`[0.0, 1000.0]` with a `HullWarning` (the step functions' cap, `steps.py`, D12's rule).

* **confirm** (recommended, confidence ~90%). the image of a set under a step function *is* a set
  of points; returning the hull would throw away what a multi-interval exists to keep (`sign`,
  `floor` of a solver box, a `//` or `%` built on `floor`). the hull is one call away
  (`.hull`), 1788's answer is the layer's, and no vector is a row (the adapter hulls). cost of the
  cap: a `HullWarning` past 1000 pieces, documented.
* **change to the hull**: a semantic loss and a churn of `steps.py`, `modulo.py` and their tests
  for 1788's sake, which the layer already provides. when it would be better: never for this
  library; a user wanting the hull has it.

### 7.2 a rounded end is open (M12)

**verified 2026-10-03**: `OutwardMultiInterval(0.1) + 0.2` is `(0.3, 0.30000000000000004)`, both
ends open; `0.30000000000000004 in` it is `False`; the layer's `Interval(0.1) + 0.2` is `[0.3,
0.30000000000000004]`, closed, and the membership is `True`. exact operands never round
(`OutwardMultiInterval(1, 10) / 3` is `[1/3, 10/3]`, closed), so this shows only on float operands
that rounding moved.

* **confirm** (recommended, confidence ~85%). the rule is the library's one attainment principle
  ("attainment is decided on exact values", `v2-plan.md` "arithmetic", "flags at rounded ends"):
  the true value lies strictly inside the one-ulp box, so an open end is the *true* statement and
  a closed one would claim a point nothing attains. a 1788 porter sees closed ends in the layer, as
  1788 has them. cons to live with: `==` between an outward result and a parsed closed literal is
  False, and a user reading `(0.3, 0.30000000000000004)` must know what the parentheses mean (the
  README row says it).
* **change to closed**: 1788's convention, every other library's. pros: fewer surprises for
  porters using the library directly. cons: loses the one bit that distinguishes "this double is
  attained" from "the value is near this double", which `is_degenerate`, the step functions and
  the solver's proofs read; it is also M12's whole mechanism (the flags come from the exact
  value), so this is not a toggle but a redesign. when better: never for the library; the layer
  is the closed view.

### 7.3 the category "degenerate infinities"

**verified 2026-10-03**: the library's `atanh([1])` is `[inf]`, `log([-inf, 0])` is `[-inf]`,
`pown_rev([0], -2)` is `{[-inf], [inf]}`; the layer's are `[empty]` each (attained infinities
dropped by the output rule). the category covers 63 vectors (36 keys) in the adapter, every one
matched through the layer (plan §2 M16b record).

* **confirm** (recommended, confidence ~90%). it is a corollary of two owner decisions, D1/D6
  (±inf are points, `[inf]` is legal) and the domain-end rule ("the end of a function's domain is a
  point of it where the one-sided limit exists", `v2-plan.md` "2026-09-25 revision", the M12
  bullets), and the name is exact: a one-point set at infinity. 1788's functions are functions of
  reals, so it has nothing to say there; the layer says 1788's nothing.
* **change** would mean dropping the limit points (`log([0])` empty), i.e. 1788's reals-only model
  inside a library whose line has ±inf as points: inconsistent with D1/D6 and with `1 / [0, 1]`
  being `[1, inf]`. not an option on its own.

### 7.4 the category "cut-based relations"

**verified 2026-10-03**: `MultiInterval(1, 2).allen(MultiInterval(2, 3))` is `Allen.OVERLAPS`;
`ieee1788.overlap(Interval(1, 2), Interval(2, 3))` is `Overlap.MEETS`. 7 vectors (5 keys).

* **confirm** (recommended, confidence ~90%). the library's relations are relations between
  *sets*: `[1, 2]` and `[2, 3]` share the point 2, so they are not disjoint and do not merely touch;
  `[1, 2)` and `[2, 3]` meet (tile with no shared point), a distinction 1788's closed intervals
  cannot express (`v2-plan.md` "comparisons": "cuts make the taxonomy finer than classical allen").
  1788's `overlap` is a relation on the ends as extended reals, and the layer gives it in full
  (sixteen states, `ieee1788.py::Overlap`). each is right for its objects.
* **change** would make `allen` on sets lie about a shared point (and break JEPD on cuts, which
  `allen_matrix` relies on, `v2-plan.md` "comparisons" M16c bullet). no.
