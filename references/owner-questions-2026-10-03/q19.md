# Q19: is the outward class isotone across number types? (report, 2026-10-03)

read-only advisory for the owner. python probes under `.scratch/owner-questions/probes-q19/`.
sections are appended as written; a section marked `(pending)` was not reached.

## 1. the question and what is built today

**the question** (HANDOFF.md "open questions for the owner", Q19 bullet, 2026-10-03): the x50 fuzz showed that
`OutwardMultiInterval` is not inclusion-isotone across number types: `A ⊆ B` does not give `f(A) ⊆ f(B)` when a
float piece of A lies in an exact piece of B. keep (the default), or make the class isotone by rounding an exact
result whenever the operand set mixes in floats, at the cost of "exact operands give the same set"?

**what is built** (verified by reading; probes in section 2 confirm the examples):

* the contract, three places that must agree: `intervals/multi_interval.py::OutwardMultiInterval` docstring ("exact
  operands give the same results as in MultiInterval"); `tests/test_outward.py` module docstring ("on exact operands it
  is the same as MultiInterval: nothing is rounded there") pinned by `tests/test_outward.py::test_exact_operands_give_the_same_set`
  and `::test_exact_operands_give_the_same_set_in_the_functions`; `v2-plan.md` "arithmetic" bullets **rounding** ("int
  and Fraction are exact and never rounded") and **flags at rounded ends** ("an exact operand never loses its true
  value"). README.md "rounding" bullet says the same in user terms. README makes NO isotonicity claim (grep
  `isoton|monoton` in README.md: no hit, 2026-10-03); `v2-plan.md` cites isotonicity twice, both as the reason for
  D7 (`1/[0]` = `∅`: "solvers (bisection, forward-backward contraction) need isotone ops"), i.e. as a design value
  the library leans on, not as a promise made to users.
* **three typing rules already coexist in the library** (which operand decides "round or not"):
  1. **per corner** (the applicator's ops `+ - * / **`, the elementary functions via `functions._Function.end`): a
     corner whose values are all exact stays exact, a corner holding a float rounds. so `O([1.0, 2]) + 1/3` =
     `(1.3333333333333333, 7/3]`: one end rounded and open, the other exact and closed, inside ONE piece.
  2. **per piece** (the step functions, `intervals/steps.py::step` line 119 `as_float = is_float(lo) or is_float(hi)`,
     then `rounding.round_piece`): a piece with any finite float end lists every value of its image as a double or
     the open gap around it; a piece with exact ends lists exact values.
  3. **per operand set** (`ops.fma` lines 485-490, `modulo` lines 120-126 and 328-343, `functions.hypot` line 655/746,
     `numeric.mid/wid/rad/mag/mig`, `cancel_minus`): computed exactly on `exact_cuts`, rounded once iff ANY operand
     has a finite float (`rounding.has_finite_float`). this is already the rule Q19's "make it isotone" option
     describes, and, as section 4 shows, it is NOT isotone either.
* **where isotonicity holds today** (the oracle `tests/test_steps.py::_assert_isotone`, and the plan §2
  "fuzz-steps-isotone" diagnosis): in the exact class on exact operands; in the outward class where every float
  piece of A lies in a float piece of B (`_float_pieces_in_float_pieces`; outward rounding is monotone and an exact
  value lies in its own open gap, so exact-A-inside-float-B is fine too). the failing shape is exactly one: **a
  float piece of A inside an exact piece of B**; there f(B) is the exact image and f(A) is its double cover, which
  sticks out by up to one ulp at each non-double value. what does hold there is `f(A) ⊆ cover(f(B))` (`_cover`,
  the tightest double-ended cover), and that is what the oracle now checks; the library was not changed.
* **every other isotonicity test in the suite runs on exact operands** (verified 2026-10-03): `tests/test_ops_properties.py::test_isotone`
  (`subset_pairs`), `tests/test_functions.py::test_isotone` (`exact_cut_tuples`), `tests/test_numeric.py::test_isotone_on_exact_operands`
  plus a float-only `::test_isotone_on_float_operands`, `tests/test_reverse.py::test_isotone`, `tests/test_modulo.py::test_isotone`,
  `tests/test_cancel.py::test_isotone_in_a_antitone_in_b`, `tests/test_pow_rev.py::test_pow_rev_isotone_and_distributive`.
  so until the x50 run nothing in the suite asked the cross-type question; `test_steps.py::test_isotone` was the only
  one drawing `float_operands`, and the mixed case is rare enough that it needed x50.
* **the 1788 layer is unaffected**: `intervals/ieee1788.py` converts every input to doubles at construction
  (`Interval(Fraction(1, 10))` is `[0.09999999999999999, 0.1]`, module docstring line 17; `_interval_of`, lines
  122-123 round down/up), so inside it every piece is a float piece and isotonicity holds by rule 1/2 above.

## 2. who relies on which property

### 2a. who relies on "exact operands give the same set" in the outward class

* **the solver's exact points** (`intervals/solver.py`): `_simplest_point` (`_simplest_between`, continued fractions)
  builds `OutwardMultiInterval(Fraction)` points and `_finish_box` outputs one "alone, as a unique zero if F is
  exactly [0] there". pinned by `tests/test_solve.py::test_simple_rational_zeros_are_exact_points` on the `EXACT`
  table (line 280): the `kink` case outputs the zero `(1/6, 1/4)`, and 1/6 is not a double. the same file's
  `_points` falls back to the exact midpoint of a component "narrowed to two adjacent doubles so it can still be
  stepped", and `newton` keeps int/Fraction ends exact (plan "newton" bullet: "int and Fraction stay exact").
  if exact operands were rounded per op, `3 * O(1/6) - 1/2` would be a gap around 0, never "exactly [0]", so a
  rational zero on a split face would come out as unproved boxes, not a unique exact point: the `kink` row goes
  red and a real capability (uniqueness at a zero where krawczyk cannot fit a set inside the interior) is lost.
  verified by probe (`p2_solver_shape.py`, 2026-10-03): where krawczyk DOES prove the zero (`newton(3x-1, [0, 1])`,
  `solve((3x-1, y-x))`) the output is already the double gap `(0.3333333333333333, 0.33333333333333337)`, so the
  exact-point output is the fall-back path only, not the common case.
* **the four exact-operand pins**: `tests/test_outward.py::test_exact_operands_give_the_same_set` (every op) and
  `::test_exact_operands_give_the_same_set_in_the_functions`, and `tests/test_steps.py::test_hull_past_the_cap`
  (the plan §2 "fuzz-steps-isotone" says a rounding fix turns the `round` rows of all three red).
* **cancel_minus's certificate**: plan "cancellation" bullet, rounding: the outward result "is not a certificate
  that B + X ⊆ A, which a moved end can break by an ulp; exact operands (a float as Fraction(f)) give that" — the
  documented way to get an exact certificate IS to feed exact operands to the outward class (or to MultiInterval,
  which is the same set then).
* **users mixing exact constants with float data**: `O(x) * Fraction(1, 3)` is tighter than `O(x) * (1 / 3)` because
  the constant never rounds; this survives any per-op rounding of the RESULT, so it is not an argument for the
  current rule by itself. what the current rule adds is that CHAINS of exact-only steps stay exact (`(O(1) / 3) * 3`
  is `[1]`; probe 3) and that an exact end of a mixed piece is kept exact and closed through an op (`7/3]` above).

### 2b. who relies on inclusion isotonicity, and whether any of them relies on the cross-type case

* **the library's own design**: `v2-plan.md` uses isotonicity as the reason for D7 (`1/[0]` = `∅`) and names
  "solvers (bisection, forward-backward contraction)" as needing isotone ops. the solver here, read in full
  (`intervals/solver.py`), needs SOUNDNESS at every step: prune by `0 ∉ f(piece)`, the newton/krawczyk set as an
  enclosure of the mean-value form, `unique` kept by later steps because the zero stays in the sub-piece, "a point
  is unique iff F is exactly [0] there". none of those steps compares f(child) with f(parent). non-isotonicity can
  only cost it efficiency (a child pruned later than the parent's bound would allow), and only by an ulp.
  **verified by probe** (`p2_solver_shape.py`): bisecting the exact piece `[1, 2]` at the float midpoint 1.5 gives
  children whose images are inside the parent's, and `f(left) | f(right) ⊇ f(parent)` (the direction the solver
  uses) holds. the solver mixes types all the time (exact user box, float midpoints, `OutwardMultiInterval(0)`,
  `Fraction` simplest points), and would be the first victim if cross-type isotonicity mattered for correctness;
  it does not.
* **users who rely on isotonicity**: subdivision schemes that assume the union of the children's ranges is inside
  the parent's (adaptive range plotting, monotone refinement of a global-optimisation bound, contractor
  fixed-point arguments of the form "X_{k+1} = X_k ∩ f(X_k) is monotone decreasing"). the practical harm is an
  ulp-wide protrusion at a boundary, which such schemes tolerate (they must already tolerate outward rounding).
  the conceptual harm is bigger than the numeric one: "A ⊆ B ⇒ f(A) ⊆ f(B)" is the first theorem in every
  interval text and a user who checks it as a sanity test, as this repo's own fuzz did, will file it as a bug.
* **the 1788 layer** (`intervals/ieee1788.py`) needs isotonicity for conformance only to the extent 1788 asks
  (section 3), and it is all-doubles inside, where isotonicity holds by monotone directed rounding.
* **the test suite** relies on the exact-operand version everywhere (section 1); only `test_steps.py::test_isotone`
  drew floats, and it is now type-aware. no test of the library asserts cross-type isotonicity any more.

### 2c. how big and how frequent the failure is, per typing rule (probes 1 and 4; measured 2026-10-03)

the three rules of section 1 fail differently, which matters for the options:

* **rule 1, per corner** (`+ - * /`, functions): an exact corner of A stays exact even when A's other end is a
  float, so a child sharing an end with its exact parent keeps that end bit-for-bit. the failure needs A's float
  end to be within about one result-ulp of B's exact end (the Q19 `+` row: `1.0` vs `1 - 10 ** -30`), or A's
  float end to be B's exact end re-typed. with ends well apart it does not happen (probe 4's random census,
  numbers below).
* **rule 2, per piece** (the step functions): every value of f(A) that is not a double is a gap, every value of
  f(B) is exact; the failure needs only one non-double value in the image (`1/10`), wherever A sits inside B.
  this is why the x50 fuzz found the steps and nothing else.
* **rule 3, per operand set** (`fma`, `%`, `//`, `hypot`, `cancel_minus`, numeric): a float ANYWHERE in the operand
  set rounds every end of the result, the exact shared end included: `fma(O([1.5, 2]), 1, 1/3)` is
  `(1.8333333333333333, 2.3333333333333335)`, not inside `fma(O([1, 2]), 1, 1/3)` = `[4/3, 7/3]`, while
  `O([1.5, 2]) + 1/3` = `(1.8333333333333333, 7/3]` IS inside `O([1, 2]) + 1/3`. so rule 3, the rule the Q19 option
  "round an exact result whenever the operand set mixes in floats" would make universal, is the LEAST isotone of
  the three across types, not the most.

**probe 4 numbers** (`p4_rule1_vs_rule3.py`, 2026-10-03, 2000 random float pieces A strictly inside random
exact-Fraction pieces B, ends well apart, `seed 20261003`): failures of `f(A) ⊆ f(B)`: `+ 1/3` 0, `* 1/3` 0,
`fma(., 1, 1/3)` 0, `% 3/7` **1178** (59%), `round(., 1)` **1939** (97%). `%` fails because the image's end `3/7`
is shared by every A and B and rule 3 rounds it for A only; `fma` fails only at a shared OPERAND end (the
`[1.5, 2]` row above), which the random draw avoids. for rule 1, scanning `B = [1, 1 + 2^-k]` with A's float end
at `1 + 2^-(k+1)`: `+` and `*` stay isotone through k = 50 and fail at k = 52 and 53, i.e. only when B is a few
ulps wide, the solver's end-game, where a 1-ulp protrusion is noise.

## 3. what 1788 and other libraries do

(from the agent's knowledge, 2026-10-03, one web search for confirmation; not verified against the standard's
text. treat the 1788 clause claims as medium confidence, the library facts as high.)

* **IEEE 1788-2015** has exactly one number format per interval type (a "bare interval type" T is built over one
  number format; binary64 for `infsup binary64`). Level 2 asks each operation for an enclosure of the Level 1
  result, graded tightest / accurate / valid; "tightest" is the T-hull of the exact result. inclusion isotonicity is
  not, to my recollection, a separate Level 2 requirement: it follows for the tightest mode because the hull in T
  is monotone, and for the other modes it is not promised (the arXiv note "About the accurate mode of IEEE
  1788-2015", 2023, discusses how under-specified accurate mode is). the question "a float piece inside an exact
  piece" cannot arise in 1788: there is no exact piece. this library's `ieee1788` layer follows that exactly, so
  its conformance is untouched by any Q19 choice.
* **MPFI**, **Boost.Interval**, **IntervalArithmetic.jl**, **mpmath.iv**, **pyinterval**, **Sage RIF**: one number
  format per interval type (mpfr at a fixed precision, a C++ `T`, `Float64`, an mpf at the context precision,
  double, a field precision). an exact rational input is converted at construction, outward, to that format
  (`interval(1//3)` in Julia, `RIF(1/3)` in Sage, `Interval(Fraction(1, 10))` in this repo's own `ieee1788`). so all
  of them are isotone trivially, by monotone directed rounding inside one grid, and none of them offers what
  `OutwardMultiInterval` offers: an exact `Fraction` end that survives a chain of ops untouched.
* **exact set libraries** (SymPy `Interval`/`Union`, Mathematica `Interval` over exact numbers): isotone because
  nothing rounds; they have no float grid at all.
* **Arb/FLINT** (used by `tests/test_oracle_flint.py` as an oracle): ball arithmetic, not sets; inclusion
  isotonicity is not a property it states, and its radius bookkeeping is not monotone in the input ball either.

**the lesson**: every precedent gets isotonicity by having ONE grid, so that f(A) and f(B) are rounded to the same
grid. this library has two grids in one set (the rationals and the doubles) and rounds a result to the grid of its
operands. the cross-type failure is the price of that, not a bug in the rounding; the only way to buy it back is to
round everything in the outward class to the double grid (option B1 below), which is what every precedent does and
what makes them unable to do what the solver's `_simplest_point` does.

## 4. the options

### A. keep the rule; document the property that does hold (the status quo, made explicit)

**meaning**: no library change. state in `README.md` ("rounding" bullet), the class docstring and `v2-plan.md`
"arithmetic": "exact operands give the same set as MultiInterval. inclusion isotonicity holds inside one number
grid: whenever every float piece of A lies in a float piece of B (an exact A inside anything included). a float
piece of A inside an exact piece of B gets f(A) ⊆ the tightest double-ended cover of f(B)". that is precisely what
`tests/test_steps.py::_assert_isotone` now checks.
**pros**: zero cost; keeps the solver's exact points, the three pin groups and the library's distinguishing feature
(an exact end survives a chain of ops); the property stated is true for all three typing rules (probe 3: every
Q19 row satisfies `f(A) ⊆ cover(f(B))`); no result of any user changes.
**cons**: the fundamental theorem is not literally true for mixed sets; a user who sanity-checks it with mixed input
files a bug; the suite's other isotonicity tests must stay exact-only or type-aware forever (a maintenance rule, not
a cost yet).
**when better**: when the users are the ones the plan already names, the solver and people mixing exact constants
with float data, and when "exact stays exact" is a selling point. that is this repo today.

### A+. option A plus a public coercion onto the double grid

**meaning**: A, plus one additive method, e.g. `A.rounded()` (name open): every finite end made a double, outward,
moved ends open, i.e. `rounding.float_cuts(cuts, outward=True)` exposed (today internal; no public equivalent exists,
grep 2026-10-03). documented next to the isotonicity statement: "to get isotonicity across your whole computation,
put the inputs on one grid: `A.rounded()`". the exact class could get it too (to nearest) for symmetry.
**pros**: everything A has; gives the isotonicity-dependent user a one-line opt-in with no new class and no change
to anyone's results; pre-2.0 it is free to add and never needs removing.
**cons**: one more method; a user has to know to call it (the doc sentence does that).
**when better**: same as A, plus any user who writes subdivision schemes over mixed input. this is my pick.

### B1. the outward class holds doubles only: every result rounded outward to the double grid

**meaning**: `OutwardMultiInterval` becomes a 1788-style type: an exact operand is used exactly INSIDE an op (so
`O(x) * Fraction(1, 3)` keeps its tightness) but every finite end of a RESULT is a double, moved ends open. exact
operands no longer give the same set as MultiInterval (`(O(1) / 3) * 3` is `(0.9999999999999999, 1.0000000000000002)`,
probe 3). at construction `O(Fraction(1, 3))` either stays exact until the first op or rounds at once (the latter is
what every precedent does and is simpler to state).
**pros**: inclusion isotone across all inputs (probe 3: all Q19 rows pass with f(B) covered; monotone rounding into
one grid); matches every other library and 1788; bounds Fraction growth in iterative use (the exact chain in probe 2
grew to 288-char ends in 300 iterations, 2026-10-03); the type story is simpler ("outward = doubles").
**cons**: loses the solver's exact-point output (`tests/test_solve.py::test_simple_rational_zeros_are_exact_points`,
`kink`'s `(1/6, 1/4)`, and the uniqueness proof that comes with "F is exactly [0]" at a rational on a split face;
`_points`' exact-midpoint fall-back would also need the exact class); turns red `tests/test_outward.py::test_exact_operands_give_the_same_set`,
`::test_exact_operands_give_the_same_set_in_the_functions`, `tests/test_steps.py::test_hull_past_the_cap` (and every
`== MultiInterval` cross-class assertion on exact operands); changes results for every user with int/Fraction ends
(a `[1]` becomes a gap); contradicts plan D3 ("int and Fraction exact, never rounded") and the README table row
"numbers"; removes the only feature no precedent has.
**when better**: if the intended user is a 1788-style numerics user who wants a float type with sets and never
wants a Fraction back, and if the solver is willing to prove rational zeros some other way. not this repo's stated
direction, but a coherent product.

### B2. round the result whenever the operand set mixes in floats (the HANDOFF wording; rule 3 everywhere)

**meaning**: generalise `fma`/`%`/`hypot`'s rule to every op: compute exactly, round every end iff any operand has a
finite float; exact-only sets stay exact.
**pros**: keeps "exact operands give the same set" literally (no float, no rounding).
**cons**: **it is not isotone** (probe 3: with `B = [1 - 10**-30, 2]` purely exact, f(B) stays exact and
`O([1.0, 2]) + 1/3` still sticks out; the failing shape "float A inside exact B" is untouched by definition). and it
makes the mixed case WORSE than today: rule 3 rounds the shared exact end too, so `fma(O([1.5, 2]), 1, 1/3)` is not
inside `fma(O([1, 2]), 1, 1/3)` while `+` is (probe 4), and `%` failed 59% of random mixed pairs. it also changes
every mixed-piece result of every op. **dominated**: pays most of B1's price and buys none of its isotonicity.
**when better**: never for Q19's purpose. (its one merit, simpler code than per-corner typing, is why fma has it.)

### B3. one type per piece everywhere (rule 2, the steps' rule, generalised)

**meaning**: a piece with any finite float end rounds all its result values. **cons**: this is the rule under which
the fuzz FOUND Q19 (97% of random mixed `round` pairs fail, probe 4); not isotone across types, and it rounds exact
shared ends. dominated like B2. (listed because Q20's third alternative is this rule for the exact class.)

### C. a third class: doubles-only outward, alongside the current two

**meaning**: `OutwardMultiInterval` stays as is; a subclass (say `FloatOutwardMultiInterval`) applies B1's rounding
once per result. honours the plan's rule "rounding is a property of the type, never a flag or context manager", which
rules out a per-class flag.
**pros**: both contracts available, each literally true for its type; isotone users pick the new class.
**cons**: a third class through every reflected dunder, `Dual`, `DecoratedInterval`, numpy, the formatter, and every
class-parametrised test (the suite already runs most vectors twice; a third pass is tens of minutes of gate time);
the `ieee1788` layer is already 90% of this (all-doubles, isotone) for anyone who wants 1788 semantics; and A+'s
coercion gives the same effect with one method. **when better**: if a real user group asks for a bare doubles-only
multi-interval with open ends and no 1788 input rules; not before someone asks.

### D. the step functions list exact values whatever the operand type (a steps-only fix)

**meaning**: `round/floor/ceil/trunc` return the exact rational values (they are always rational), in both classes,
so the steps become isotone and class-equal. **cons**: Fraction ends emerge from float inputs (`round(O(0.15), 1)`
→ `[1/5]`) and infect the rest of the computation; departs from python's float `round`; fixes the symptom the fuzz
hit and not `+`'s ulp case. not recommended as Q19's answer; a possible later tightening if the owner wants the
steps "decimal-exact".

### note, outside Q19's scope: rule 3 ops could move to rule 1

`fma`, `%`, `//`, `hypot`, `cancel_minus` round an exact shared end whenever a float is anywhere in the operand set
(section 2c). typing them per corner, as the applicator does, would make them tighter at exact ends and as isotone as
`+`. not needed for 2.0; it is a tightening with no contract change.

## 5. recommendation, confidence, what would change my mind

**recommendation: A+** — keep the library as it is; write the true property into README, the class docstring and the
plan ("isotone inside one grid; across grids f(A) ⊆ the tightest double cover of f(B); exact operands give
MultiInterval's set"); add one public method that puts a set on the double grid outward, so a user who needs the
fundamental theorem verbatim can have it by choosing one grid, as every other library forces them to anyway.
**confidence 0.8.**

why, in order of weight:
1. the only option that buys isotonicity is B1 (or C, B1 as a third class), and it costs a pinned solver capability
   (`test_simple_rational_zeros_are_exact_points`), three pin groups, plan D3, and the one feature no precedent has.
   the owner's design values (D3 exact numbers, D7's "solvers need isotone ops") were both honoured by the same
   person; where they collide, the solver, the named beneficiary of isotonicity, needs soundness, not isotonicity
   (section 2b, read in full; probed), so D3 wins on the evidence.
2. the option the HANDOFF bullet actually words ("round an exact result whenever the operand set mixes in floats",
   B2) does not deliver isotonicity (probe 3) and is the least isotone rule of the three already in the library
   (probe 4). if the owner's instinct was "there must be a type rule that fixes this", the plan's own diagnosis is
   right: no rule by number type can, only one grid can.
3. what fails is bounded and statable: under the applicator's per-corner rule, a 1-ulp protrusion when A's float
   end is within an ulp of B's exact end (k >= 52 in probe 4); under the steps' per-piece rule, the double cover of
   each exact value. "f(A) ⊆ cover(f(B))" is exactly true, already the oracle, and is what a 1788 user would get
   from their own library's rounding anyway.
4. 2.0 is unreleased, so the cheap, additive A+ is free now; the breaking B1 is not needed by any user named in the
   plan.

**what would change my mind**: (a) the owner naming a target user who writes monotone-refinement schemes over MIXED
input and cannot call `.rounded()` first; (b) the owner deciding that Fraction ends in results are an anti-feature
and the solver's exact points not worth keeping, in which case B1 is the honest design and should be done before
2.0, not after; (c) a soundness bug (not an isotonicity one) traced to a mixed piece, which would say the two-grid
design is too subtle to keep, and would also point to B1.

## 6. cost of changing later: before vs after 2.0

* **A / A+ now**: a doc edit plus one additive method; docs skip the fuzz (owner 2026-09-30), the method needs the
  gate (~15 min) and a prepush x10 (~83 min, 2026-09-29 measurement). nothing to undo later.
* **B1 before 2.0** (estimate, not measured): the rounding itself is one `float_cuts(..., outward=True)` at the end of
  each outward op (the hook already has every end), half a day; the fallout is the real cost: `solver._simplest_point`
  / `_points` rework or acceptance of lost exact points, three pin groups rewritten, D3 and the README "numbers" row
  re-stated, every `outward.cuts == nearest.cuts` cross-class assertion re-thought, a full gate and x10 fuzz cycle,
  and the CORE-MATH manual check does not apply (the scalar evaluator is untouched). one to two days plus the runs.
* **B1 after 2.0**: every user with int/Fraction ends gets different results (`[1]` → a gap), the solver's output
  type for rational zeros changes, and the class docstring's promise is broken: a major-version change.
* **the reverse direction (B1 now, A later)** is just as breaking: users who learnt "outward = doubles" would get
  Fractions back. so the decision binds at 2.0 whichever way; it should be taken now, and A+ keeps the current
  promises while adding the escape hatch.
* **C after 2.0** is additive (a new class) and stays possible at any time; it is the natural fall-back if a user
  group for B1 appears after release.

## 7. Q20 glance: the crossed piece in the exact class

Q20 (HANDOFF bullet below Q19; plan §2 "fuzz-rootn-crossed"): to nearest, `rootn((10 ** -30, 1.0000000000000003e-30], 5)`
typed each end on its own (rule 1, per corner, in `functions._Function.end` and `reverse._end`): the exact end gives
`1/10 ** 6` exactly, the float end rounds to nearest onto `1e-06`, which is BELOW it, and the piece crossed. the fix
built: the piece between the two values, each keeping its flag, `[1e-06, 1/1000000)`. alternatives listed: both ends
closed; or round the exact end too whenever its partner is a float (one type per piece, rule 2).

how Q19 bears on it: Q19 and Q20 are the same design axis, "which operand decides the type of a result value", and
Q19's evidence (section 2c) is that rule 1 (per corner) is the rule that breaks isotonicity LEAST and keeps shared
